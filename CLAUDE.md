# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

MakeASound is a C++20 static library that gives platform-agnostic access to audio and MIDI. Two façades make up the device library's public surface, and a second static target builds a plugin core on them:

- `MakeASound::DeviceManager` — audio device enumeration and streaming, backed by [miniaudio](https://github.com/mackron/miniaudio).
- `MakeASound::MidiManager` — MIDI input/output ports, backed by the platform's own MIDI API: Core MIDI on macOS and iOS, WinMM on Windows, the ALSA sequencer on Linux. A platform with none of those fails at configure time rather than building a façade with nothing behind it.
- `MakeASoundPlugin` — the SDK-free plugin core: `Plugin`, parameter groups, versioned state, the module description and `PluginWrapper`, the per-block pipeline every format adapter shares. `plan.md` holds the stages.
- `MakeASoundDSP` — the optional DSP library, built always and linked only by what asks for it: today `DSP::TestSynth`, the instrument `Apps/Synth` and `Plugins/Synth` both play.
- `MakeASoundStandaloneCore` — a `Plugin` run without a host and without a window (`StandaloneHost`: devices, MIDI, the wrapper, `Engine` and the settings file), built wherever the plugin core is, Linux and iOS included.
- `MakeASoundPluginUI`, `MakeASoundPluginWeb` and `MakeASoundStandalone` — each built where the eacp target it needs exists: the generic parameter editor every format shows for a plugin with no editor of its own and the resize grip, an `Editor` over eacp's `WebView` for a plugin whose editor is a React page, and the standalone format's default app, a `StandaloneHost` with its editor and device and MIDI pickers: windows and a menu bar on macOS and Windows, one screen on iOS.
- `MakeASoundVST3` — the VST3 format, a single-component adapter over `PluginWrapper` and the vendored SDK, built wherever `vst3sdk` is on a desktop; pluginval at strictness 10 is its proof.
- `MakeASoundAU` — the AU format, macOS only: one Audio Unit v2 class (`MusicDeviceBase`) over `PluginWrapper` and Apple's AudioUnitSDK (fetched as `ausdk`), built wherever `ausdk` is; `auval -strict` after an install step is its proof.
- `MakeASoundAUv3` — the AUv3 format, an `AUAudioUnit` subclass over `PluginWrapper` in Objective-C++ with no SDK, built on every Apple platform, with its view (an `AUViewController` that is the extension's principal class) where eacp's UI tier is: it ships on iOS, an app extension inside the plugin's standalone app (`FORMATS ... AUv3`), and macOS runs its suites; `Tools/AUv3Probe` in the simulator is its proof. CLAP is a later stage.

Each façade hides its backend behind a pimpl, so no backend types leak into the public headers. The audio side has one backend today; the MIDI side has one per platform behind that same seam.

## Build

Dependencies are fetched automatically by [CPM.cmake](CMake/CPM.cmake) the first time CMake configures — no manual install. The library pulls in miniaudio, [Miro](https://github.com/eyalamirmusic/Miro) (reflection/serialization) and `ea_data_structures`; the demo apps additionally pull in `eacp` (web-UI host), and the plugin core links its `eacp-core` module. The MIDI backends need nothing fetched — they are the platform's own. Their transitive deps (e.g. ResEmbed, NanoTest) come along automatically. Linux additionally needs the ALSA development headers (`libasound2-dev`) installed on the machine — the sequencer backend links against them — and, with the plugin core on, the dev packages eacp's Linux graphics tier configures against (Wayland, xcb, xkbcommon, libdecor, FreeType, HarfBuzz, fontconfig) plus libcurl for eacp-network; `.github/workflows/ci.yml`'s apt step is the list. The tests additionally pull in [ScopedMemoryAllocations](https://github.com/eyalamirmusic/ScopedMemoryAllocations) — **test-only**: `AllocationsChecker` is an INTERFACE target whose sources compile into whatever links it and interpose `malloc`/`new`, so it belongs to `MakeASoundTests` and must never reach `Lib/` or `Apps/`.

```bash
cmake -S . -B build -G Ninja
cmake --build build
./build/Apps/Example/Example     # plain CLI: streams white noise for 2s
./build/Apps/MidiDemo/MidiDemo   # plain CLI: MIDI demo
```

`Apps/Demo` and `Apps/Synth` build macOS `.app` bundles with web (React/Vite) UIs hosted via `eacp`/Miro's webview; their web assets are bundled at build time. `Apps/Synth` links `MakeASoundDSP` and runs its `TestSynth` on `Engine` behind the web page's gain slider and MIDI log.

A plugin is built with `makeasound_add_plugin` from `CMake/MakeASoundPlugin.cmake`, which the top-level `CMakeLists.txt` includes whenever the plugin core is built, so a CPM consumer calls it from its own tree:

```cmake
makeasound_add_plugin(Gain FORMATS Standalone VST3 AU AUv3 OUTPUT_NAME "MakeASound Gain" SOURCES GainPlugin.cpp)
```

It compiles the sources once as the static core `<Name>` (linking `MakeASoundPlugin` PUBLIC) and adds one target per format:

- `<Name>-Standalone`, an executable built from `Plugin/Standalone/StandaloneMain.cpp` (`eacp::Apps::run<StandaloneApp>()`), on Apple a `MACOSX_BUNDLE` with `NSMicrophoneUsageDescription` unless `NO_AUDIO_INPUT` says the plugin declares no input bus (the Synth passes it; the layout is known only at run time, so the flag is the caller's to keep true), on iOS `UIBackgroundModes` `audio` too, at `VERSION` (`EACP_APP_VERSION`, which eacp writes into the plist), and on macOS an ad-hoc `codesign` post-build. On iOS (`_makeasound_ios_bundle`) Ninja adds `CFBundleSupportedPlatforms` (`iPhoneSimulator` when `CMAKE_OSX_SYSROOT` names the simulator, `iPhoneOS` otherwise), `UIDeviceFamily` 1 and 2 and `MinimumOSVersion` to the plist and signs ad hoc for the simulator only, a device build staying unsigned; Xcode writes those keys itself (`TARGETED_DEVICE_FAMILY` `1,2`) and signs automatically with `MAKEASOUND_IOS_TEAM`, otherwise ad hoc (`CODE_SIGN_IDENTITY` `-`, manual) with `CODE_SIGNING_ALLOWED[sdk=iphoneos*]` NO. `STANDALONE_SOURCES <file>...` builds it from the plugin's own app instead, its `main` and app class composing `StandaloneHost` and whichever of `SettingsPanel`, `GenericEditor` and `editorWindowOptions` it wants through `<MakeASound/Plugin/Standalone/MakeASoundStandalone.h>`, and `STANDALONE_LIBRARIES <target>...` is whatever else it links. It still links `MakeASoundStandalone` (then the libraries, then the core), so the pieces are there to take while the unreferenced `StandaloneApp` objects stay out of the link, and it keeps the default app's bundle, plist, microphone string and signing; either argument without the `Standalone` format, or the libraries without the sources, is a configure error.
- `<Name>-VST3`, a `MODULE` built from the entry files recorded on `MakeASoundVST3` (`MAKEASOUND_VST3_ENTRY`, our `GetPluginFactory`) and `vst3sdk` (`MAKEASOUND_VST3_SDK_MAIN`, the SDK's `bundleEntry`/`InitDll`/`ModuleEntry`), linking `MakeASoundVST3` before the core. Every bundle lands in `<build>/VST3/<OUTPUT_NAME>.vst3`, the output directories wrapped in `$<1:...>` so a multi-config generator adds no per-config folder, and the import library and `.pdb` kept out of it in the target's own binary dir; the bundle path is the target property `MAKEASOUND_VST3_BUNDLE`. On macOS it is `BUNDLE` + `BUNDLE_EXTENSION vst3` with `Plugin/VST3/VST3Info.plist.in` (`BNDL`, identifier `<BUNDLE_ID>.vst3`, one per format because the macOS Installer resolves components by bundle id), the SDK's `macexport.exp` as `-exported_symbols_list` (so `nm -gU` shows exactly `_GetPluginFactory`, `_bundleEntry`, `_bundleExit`), and a post-build that copies `Plugin/VST3/PkgInfo` (the 8 bytes `BNDL????`) into `Contents/` and then ad-hoc signs the bundle. On Windows it is `<Out>.vst3/Contents/<arch>-win/<Out>.vst3`, the arch from `CMAKE_CXX_COMPILER_ARCHITECTURE_ID` (`x86_64`, `arm64`, `x86`); on Linux `<Out>.vst3/Contents/<CMAKE_SYSTEM_PROCESSOR>-linux/<Out>.so`, linked with `Plugin/VST3/VST3Exports.map` as `--version-script` (`GetPluginFactory`, `ModuleEntry`, `ModuleExit`, `local: *`).
- `<Name>-AU` (macOS only), a `MODULE` built from the two files recorded on `MakeASoundAU`, `MAKEASOUND_AU_ENTRY` (`EntryPoint.cpp`, the factory) and `MAKEASOUND_AU_VIEW_SOURCE` (`CocoaUI.mm`, or `NoCocoaUI.cpp` where there is no UI tier), linking `MakeASoundAU`, then the core, then `MAKEASOUND_AU_VIEW_LIBRARIES`, with `-fobjc-arc` on the Objective-C++, `OBJCXX_STANDARD 23` and Release LTO. `MAKEASOUND_AU_VIEW_CLASS` is defined per module as `MakeASoundAUView_<id>`, `<id>` being `string(MAKE_C_IDENTIFIER "<BUNDLE_ID>_<VERSION>")`, because the Objective-C runtime is one per process and two components defining one class would share whichever loaded first. The bundle, `<build>/AU/<OUTPUT_NAME>.component` (the property `MAKEASOUND_AU_BUNDLE`), is laid out by hand rather than as a `BUNDLE` target, the module landing in `Contents/MacOS` (the output directory wrapped in `$<1:...>`), because CMake rewrites a bundle target's `Info.plist` on every configure and would undo the generated one until the next relink; `MAKEASOUND_AU_EXPORTS` (`AUExports.txt`) as `-exported_symbols_list` with `LINK_DEPENDS`, so `nm -gU` shows exactly `_MakeASoundAUFactory` and `_MakeASoundAUWritePlist`. The module depends on `MakeASoundAUPlistGen`, the one plist tool every AU module shares (targets are global, so a CPM consumer's directory names it too); the module's post-build runs `$<TARGET_FILE:MakeASoundAUPlistGen>` on `$<TARGET_FILE:<Name>-AU>` to write `Contents/Info.plist` from the module's own `describeModule()` (module binary, bundle name, identifier `<BUNDLE_ID>.component`, executable, output path), copies `MAKEASOUND_AU_PKGINFO` (the VST3 directory's `PkgInfo`, the same 8 bytes) into `Contents/`, and ad-hoc signs the bundle over both. Its `CFBundleVersion` and `CFBundleShortVersionString` are `ModuleDescription::version`, not `VERSION`, because macOS caches a bundle's `AudioComponents` keyed by `CFBundleVersion`.
- `<Name>-AUv3` (iOS only, a status line elsewhere; `AUv3` without `Standalone` in the same call is a configure error, a custom app counting), the app extension `<OUTPUT_NAME>.app/PlugIns/<OUTPUT_NAME>.appex`, identifier `<BUNDLE_ID>.auv3`: an executable (no framework, so the core is linked into the app and the extension each) built from `MAKEASOUND_AUV3_MAIN` (`ExtensionMain.cpp`, a `main` over `NSExtensionMain`, declared `extern "C"` there since no header does) and `MAKEASOUND_AUV3_SOURCES` with `MAKEASOUND_AUV3_CLASS_SUFFIX` defined as the AU view's `<id>`, compiled and linked with `-fapplication-extension` and `-fobjc-arc` on the Objective-C++, linking `MakeASoundAUv3`, the core and `MAKEASOUND_AUV3_VIEW_LIBRARIES`, Release LTO; the app depends on it. Its plist, `<binary dir>/<Name>-AUv3-Info.plist` from the custom target `<Name>-AUv3-Plist`, is `writeAppExtensionPlist` run by `<Name>-Describe` (bundle name, identifier, executable, principal class `<MAKEASOUND_AUV3_PRINCIPAL_CLASS>_<suffix>`, `MAKEASOUND_AUV3_HAS_VIEW` as 0 or 1, output), then `plutil` sets `CFBundleVersion` and `CFBundleShortVersionString` to `VERSION`, since an extension's version must be its app's. **The plist tool for a cross build**: an iOS binary can be neither loaded nor run on the build machine, and the component type needs the plugin constructed, so the first `AUv3` call schedules (`cmake_language(DEFER)` to the end of the top-level configure) `MakeASoundDescribeBuild`, an `ExternalProject` that configures the same top-level project again for macOS into `<build>/MakeASoundDescribe` (Ninja, else Makefiles; Debug; `CMAKE_OSX_SYSROOT=macosx`; `MAKEASOUND_DESCRIBE_BUILD` ON, apps and tests off; `MAKEASOUND_BUILD_EXAMPLES`, `_UNITY_BUILD`, `_CI_BUILD` and `CPM_SOURCE_CACHE` forwarded, every package in `CPM_PACKAGES` pointed at the source this tree already has through `CPM_<name>_SOURCE`, so nothing is fetched again; then `MAKEASOUND_DESCRIBE_CMAKE_ARGS`) and builds every `<Name>-Describe` (`BUILD_ALWAYS`, the tools as byproducts), its steps under `cmake -E env --unset=SDKROOT --unset=IPHONEOS_DEPLOYMENT_TARGET --unset=MACOSX_DEPLOYMENT_TARGET`, since an Xcode build exports them to every script. In that build `makeasound_add_plugin` makes the core and, for an `AUv3` call, `<Name>-Describe` (`MakeASoundAUDescribe`'s `MAKEASOUND_AU_DESCRIBE_MAIN`, `DescribeMain.cpp`, plus the core) in `<sub-build>/Describe`, and returns; the top level skips `ThirdParty/`, `Apps/`, `Tools/` and `Tests/`, and `Plugin/` adds only `AU/`, so a web editor builds its fallback and runs no npm. A plugin's sources must therefore build for macOS, and a consumer's tree is configured twice. Under Ninja the extension is laid out by hand (`MACOSX_BUNDLE FALSE`, the output directory `$<1:...>` inside the app's bundle, the property `MAKEASOUND_AUV3_BUNDLE`, the plist a `LINK_DEPENDS`); its post-build copies the plist in and, for the simulator, signs it ad hoc and re-signs an already-linked app (`CMake/SignBuiltBundle.cmake`), whose own post-build signs it over the extension otherwise. Under Xcode it is a `MACOSX_BUNDLE` with `BUNDLE_EXTENSION appex`, `XCODE_PRODUCT_TYPE com.apple.product-type.app-extension`, `INFOPLIST_FILE` the generated plist (Xcode adds the platform keys; the plist must not carry them), `APPLICATION_EXTENSION_API_ONLY`, `CLANG_ENABLE_OBJC_ARC` (Xcode drops the per-language `-fobjc-arc`) and the app's signing, and the app embeds it with `XCODE_EMBED_APP_EXTENSIONS`, which copies but does not build it.

`OUTPUT_NAME` is the bundle and window name, `BUNDLE_ID` defaults to `com.makeasound.<name>` lowercased, `COMPANY` (default `MakeASound`) is the company eacp embeds in the app's `AppInfo` and the VST3 plist's copyright, and `VERSION` (default `1.0.0`) is the app's, the AUv3 extension's and the VST3 bundle's version string and part of the AU view's and the AUv3 classes' names; a VST3 host reads the plugin's version from the factory instead, which reports `PluginDescription::version`, and the AU plist takes `ModuleDescription::version`. The settings file is filed under `describeModule()`'s `vendor` and the plugin's `name()`, so the two can differ. A format whose target was not built (`MakeASoundStandalone`, `MakeASoundVST3`, `MakeASoundAU`, `MakeASoundAUv3`) is skipped with a status line, as is `AUv3` off iOS; an unknown format is a configure error. The function tests those targets and reads every file path from their properties, because targets are global where a consumer's directory cannot see MakeASound's variables. With `MAKEASOUND_INSTALL_PLUGINS` on (the default), a last post-build runs `CMake/InstallPluginBundle.cmake`, a best-effort copy (a failure is a warning) into `~/Library/Audio/Plug-Ins/VST3`, `%LOCALAPPDATA%/Programs/Common/VST3` or `~/.vst3`, and a component into `~/Library/Audio/Plug-Ins/Components`.

A plugin whose editor is a web page adds `makeasound_add_web_editor` from `CMake/MakeASoundWebEditor.cmake`, which `Plugin/CMakeLists.txt` includes after `MakeASoundPlugin.cmake`, called after `makeasound_add_plugin`:

```cmake
makeasound_add_web_editor(SynthPlugin WEB_DIR ${CMAKE_CURRENT_SOURCE_DIR}/web SOURCES SynthEditor-Web.cpp FALLBACK_SOURCES SynthEditor-None.cpp)
```

Its other arguments are `[API <type>... API_HEADER <header>...]`, Miro APIs beside `MakeASound::Web::ParameterApi`, and `[CATEGORY]` (default `<Name>Editor`). Where `MakeASoundPluginWeb` is a target it runs `miro_export` as `<Name>EditorSchema` (the API header from that target's property `MAKEASOUND_WEB_API_HEADER`) and eacp's backend, mock and React-hook generators into `<WEB_DIR>/src/generated`, links the codegen tool `<Name>EditorSchema_Codegen` against `MakeASoundPluginWeb` when it exists (not when cross-compiling, iOS included, where the committed `src/generated` stands in), and calls `eacp_webview_add_vite(<Name> NAMESPACE <Name>Editor CATEGORY <category>)`: `npm install` at configure when `<WEB_DIR>/node_modules` is missing, `vite build` in the build into the binary dir, and the result embedded through ResEmbed as an INTERFACE source of the static core, so every format target linking the core carries the page in its own image. It then links `MakeASoundPluginWeb` PUBLIC, adds `SOURCES` to the core and defines `MAKEASOUND_WEB_DEV_SERVER` for `WebEditorOptions::devServer` (`"http://localhost:5173"` under `EACP_WEBVIEW_DEV`, which skips the vite build and the embed, `""` otherwise). Where `MakeASoundPluginWeb` is not a target (Linux) it adds `FALLBACK_SOURCES` and runs no npm. Node and npm are therefore needed to configure a tree with the examples on macOS, Windows and iOS; `MAKEASOUND_BUILD_EXAMPLES=OFF` keeps a plugin-core build free of them. `<WEB_DIR>/.gitignore` keeps `node_modules`, `.vite` and `dist` out; `src/generated` and `package-lock.json` are committed. `makeasound_add_plugin` knows nothing of it: the page rides in the core.

```bash
open "./build/Plugins/Gain/MakeASound Gain.app"     # the effect example
open "./build/Plugins/GainApp/MakeASound Gain App.app"   # the effect in an app of its own
open "./build/Plugins/Synth/MakeASound Synth.app"   # the instrument example
./build/Tools/PluginValidator/PluginValidator build/VST3   # every .vst3 there, strictness 10
./build/Tools/PluginValidator/PluginValidator build/AU     # every .component there, auval -strict
```

`AUv3Probe` (`Tools/AUv3Probe/`, iOS only) is a host's first minute with an installed AUv3, as a command-line tool for `xcrun simctl spawn <udid> AUv3Probe <app or appex>...`: for each `AudioComponents` entry of each extension (an app standing for every `PlugIns/*.appex`) it waits up to 30 s for `AudioComponentFindNext` to find it with `kAudioComponentFlag_IsV3AudioUnit`, instantiates it (out of process: `AUAudioUnit_XH`), renders 16 blocks of 512 (an effect fed a 440 Hz sine at half scale through the pull block, an instrument a middle C through `scheduleMIDIEventBlock`) wanting a peak above 0.01, and asks for the view controller, printing `PASS`/`FAIL` per component and exiting with the number that failed. In a windowless process the remote controller reports the screen's size, not the editor's.

`PluginValidator` (`Tools/PluginValidator/`, added with `Plugins/` when `MakeASoundPluginval` is a target) is pluginval and auval as an executable, so CLion, CI and a test all run it the same way: `[--strictness N] [--skip-gui-tests] [--timeout-ms N] [--version vX.Y.Z] [--stress N] [--logs <dir>] <bundle or folder>...`, each `.vst3` or `.component` named and every one of either in each folder named (a directory ending in `.vst3` or `.component` is a bundle, not a folder); nothing to validate prints the usage and exits 1. A `.component` goes through auval (see `Plugin/Validation/`): it is copied into `~/Library/Audio/Plug-Ins/Components`, replacing the one there, and each of its `AudioComponents` runs through `auval -strict -v`, `--stress N` adding `-stress N`; pluginval is fetched only when a `.vst3` is among the bundles, so `PluginValidator build/AU` touches no network. It depends on no plugin target and has no compiled-in folder, so it validates a bundle from any tree, and running it from CLion does not build the plugins first. The first run downloads Tracktion's pluginval v1.0.4 into eacp's resource folder (`OnlineResource::defaultDirectory()`, under the app's Application Support); later runs find it there and touch no network, and a new `--version` downloads again. It runs each bundle with `--strictness-level 10 --timeout-ms 120000 --verbose`, prints `PASS <name> (N s)` or `FAIL <name> (exit N, N s)` with the last 25 non-blank lines and the path of the full log (`<logs>/<bundle>.log`, the system temp folder's `PluginValidator/` unless `--logs` says where), and exits with the number that failed. Tracktion publishes no Windows ARM64 build, so there it stops with an error. Its editor tests open each editor briefly; nothing plays. Off macOS a `.component` fails with "AU validation is macOS only".

To point CPM at a local checkout of a dependency instead of fetching, pass e.g. `-DCPM_Miniaudio_SOURCE=/path/to/miniaudio` at configure time.

CMake options: `MAKEASOUND_UNITY_BUILD` (jumbo build of our own targets, the example plugin cores included, OFF), `MAKEASOUND_CI_BUILD` (OFF; the flag set CI configures with: it forces `MAKEASOUND_UNITY_BUILD`, eacp's `EACP_CI_BUILD`, which is eacp's unity build, Miro's and its precompiled system headers, and `ESIMD_UNITY_BUILD`, as cache entries so the dependencies see them when CPM configures them; a cold build of the plugin core compiles all of eacp and the VST3 SDK, and this is what keeps a runner's build in minutes. `CMAKE_CXX_SCAN_FOR_MODULES` is OFF project-wide, because a source CMake scans for C++ modules is left out of its unity chunk, which under MSVC and clang-cl silently turned every unity build back into one TU per file), `MAKEASOUND_INSTALL_PLUGINS` (ON: copy each plug-in bundle into the user's plug-in folder after it builds, best effort), `MAKEASOUND_IOS_TEAM` (empty: the development team an iOS tree signs its apps and extensions with under Xcode), `MAKEASOUND_DESCRIBE_CMAKE_ARGS` (empty: more configure arguments for the AUv3 plist tools' host build, for a consumer whose tree needs some), `MAKEASOUND_DESCRIBE_BUILD` (internal: set only on that host build), `MAKEASOUND_BUILD_APPS` (ON, top-level builds only) and `MAKEASOUND_BUILD_PLUGIN` (top-level builds only by default: the `MakeASoundPlugin` target and its tests; it is why the library side finds eacp at all, so a CPM consumer such as Plug or tamber-web fetches eacp only when it turns the option on), and `MAKEASOUND_BUILD_EXAMPLES` (ON, top-level builds with the plugin core only: `Plugins/Gain`, targets `Gain`, `Gain-Standalone`, `Gain-VST3`, `Gain-AU` and `Gain-AUv3`, `Plugins/GainApp` (a desktop app: only where `MakeASoundStandalone` is a target and not on iOS), the Gain plugin as `GainApp` and `GainApp-Standalone` (`MakeASound Gain App.app`) through `STANDALONE_SOURCES GainApp.cpp`: its own app, one window with a toolbar of its own (an `Audio / MIDI Settings...` button opening a `SettingsPanel` window, and the running stream) above `GenericEditor`, the window's rule `editorWindowOptions`' with the toolbar added, and its settings at `settingsPath("MakeASound", "Gain App")` through `StandaloneHost`'s plugin-and-path constructor, so it shares no file with `Gain-Standalone`, and `Plugins/Synth`, targets `SynthPlugin`, `SynthPlugin-Standalone`, `SynthPlugin-VST3`, `SynthPlugin-AU` and `SynthPlugin-AUv3` (bundle id `com.makeasound.synth`), since `Apps/Synth` owns `Synth`; both link `MakeASoundDSP` and play its `TestSynth`; Gain has a bypass parameter, and the Synth a React editor through `makeasound_add_web_editor`, its `createEditor()` calling `createSynthEditor` from `SynthEditor-Web.cpp` (a `Web::WebEditor`, 600×400, resizable 360×240..1200×800 at any ratio so it fills a phone's portrait screen, its page sizing itself from `min()` of both viewport axes, null on a Windows machine without the WebView2 runtime) or `SynthEditor-None.cpp` (null, so the generic editor shows), its page in `Plugins/Synth/web`, `useParameters.ts` over the generated backend). There is no GUI flag: `Plugin/UI/CMakeLists.txt` builds `MakeASoundPluginUI` when `TARGET eacp-ui` exists, `Plugin/Standalone/CMakeLists.txt` always builds `MakeASoundStandaloneCore` and builds `MakeASoundStandalone` when `MakeASoundPluginUI` and `eacp-graphics` exist on Apple or Windows (`APPLE OR WIN32`, iOS included); the standalone core's tests test `TARGET MakeASoundStandaloneCore`, and the window-tier tests and every `-Standalone` target `TARGET MakeASoundStandalone`, so a Linux build keeps the host and skips the window. `Plugin/VST3/CMakeLists.txt` builds `MakeASoundVST3` when `TARGET vst3sdk AND NOT IOS AND NOT ANDROID`, with the view when `MakeASoundPluginUI` and `eacp-graphics` exist and without it otherwise, and every `-VST3` target tests `TARGET MakeASoundVST3`. `Plugin/AU/CMakeLists.txt` builds `MakeASoundAUDescribe` on `APPLE` (iOS included) and `MakeASoundAU` and the executable `MakeASoundAUPlistGen` when `TARGET ausdk`, which `ThirdParty/` defines on `APPLE AND NOT IOS` alone, so Windows, Linux and iOS trees skip those with a status line, with the view when `MakeASoundPluginUI` and `eacp-graphics` exist and without it otherwise; every `-AU` target tests `TARGET MakeASoundAU`. `Plugin/AUv3/CMakeLists.txt` builds `MakeASoundAUv3` on `APPLE`, and `MakeASoundAUv3View` beside it when `MakeASoundPluginUI` and `eacp-graphics` exist. The AudioUnitSDK's headers include `<expected>`, so `ausdk` carries `cxx_std_23` PUBLIC and whatever links it or `MakeASoundAU` (each `<Name>-AU` module, and the test-only `MakeASoundAUTestModule`, which compiles the entry and view TUs for the tests and links `MakeASoundAU` PRIVATE so `MakeASoundTests` itself stays C++20) compiles as C++23; `MakeASoundAUDescribe`, `MakeASoundPlugin` and `MakeASoundAUPlistGen` never see the SDK and stay C++20, and the tests reach the adapter through the AudioUnit C API alone, never an adapter header.

IDE folders: `Lib` (and `Lib/Plugin`), `Apps`, `Plugins/<Name>`, `Tools`, `Tests`, each set through `CMAKE_FOLDER` at the top of that directory's `CMakeLists.txt`, and `External/<project>` for every target a dependency defines. `CMake/ExternalFolders.cmake` does the last one in a call deferred to the end of the top-level configure: it walks every directory and files the targets of any whose `project()` is not ours under `External/<that project>`, keeping the folder the dependency gave them below it (eacp's `ThirdParty`), so it works wherever CPM put the sources or a `CPM_<Name>_SOURCE` pointed. `miniaudio` is built by our own `FindMiniaudio.cmake`, so that file sets `External/miniaudio` itself.

`ThirdParty/VST3_SDK` is the one dependency kept in the tree rather than fetched: Steinberg's VST 3 SDK 3.8.1, MIT since 3.8.0, `base` and `pluginterfaces` whole and `public.sdk` trimmed to a single-component plugin's side, every folder's own `LICENSE.txt` alongside. `ThirdParty/CMakeLists.txt` builds it as the static target `vst3sdk` (added under `MAKEASOUND_BUILD_PLUGIN`, IDE folder `External/VST3_SDK`, always a unity build since nothing in it is ever edited, with `moduleinit.cpp` and `vstsinglecomponenteffect.cpp` kept out of the chunks: the first references the `moduleHandle` only a plugin module defines, the second must include its own header before any other has pulled in `ivsteditcontroller.h`): SYSTEM include root `ThirdParty/VST3_SDK`, `DEVELOPMENT=1`/`RELEASE=1` per configuration, CoreFoundation on Apple and pthread on Linux, and the platform's entry file and the macOS export list recorded as the target properties `MAKEASOUND_VST3_SDK_MAIN` and `MAKEASOUND_VST3_SDK_EXPORTS`, because `bundleEntry`/`InitDll`/`ModuleEntry` must be compiled into the plugin binary itself. `ThirdParty/README.md` lists the selection and how to update it, and `Tests/VST3SDKTests.cpp` links the target so every CI platform compiles it. Apple's AudioUnitSDK (Apache-2.0) is the other SDK, fetched rather than vendored: `ThirdParty/CMakeLists.txt` pulls it through CPM (`DOWNLOAD_ONLY`, `GIT_TAG AudioUnitSDK-1.4.0`) on `APPLE AND NOT IOS` and builds its twelve sources as the static target `ausdk`: SYSTEM include root `<source>/include`, `cxx_std_23` PUBLIC, its warnings off (`-w`), AudioToolbox, CoreAudio, CoreMIDI and CoreFoundation PUBLIC, IDE folder `External/AudioUnitSDK`, always a unity build. The repository itself is MIT (`LICENSE`).

CI lives in `.github/workflows/ci.yml` and builds on macOS (universal arm64+x86_64), Windows (MSVC and clang-cl, x64 and ARM64), and Linux (GCC and Clang); every desktop job and the iOS one run `actions/setup-node@v4` (Node 22, npm cache keyed on `Plugins/Synth/web/package-lock.json`) before the configure, since the Synth's web editor runs `npm install` at configure and vite in the build wherever eacp has a web runtime (Linux builds the fallback and runs no npm; the step is harmless there). Every desktop job builds both `.vst3` bundles, and macOS both `.component`s too. Entries with `pluginval: true` (macOS universal, Windows MSVC x64, Windows clang-cl x64, Linux GCC) then run `build-Release/Tools/PluginValidator/PluginValidator --logs build-Release/pluginval/logs build-Release/VST3`, Linux under `xvfb-run -a` with `--skip-gui-tests` (the runner has no display and no Vulkan device; its apt step also installs `libcurl4-openssl-dev`, which `eacp-network` links), and a failure uploads `build-Release/pluginval/logs/`. The macOS entry follows with `auval (Release)`, the same tool over `build-Release/AU` with the same `--logs`, which installs each component into the runner's `~/Library/Audio/Plug-Ins/Components` and runs `auval -strict -v` per entry; the upload covers its logs. The iOS job's two configures (device and simulator) build both examples' `-Standalone` apps; the simulator half runs the whole suite (the standalone suites included) through `ctest` and then installs and launches each app in the booted simulator, failing when one is not still running five seconds later, and then runs `AUv3Probe` over both apps, so each extension must register, instantiate out of process, render and hand back a view controller; the device half's apps are unsigned. A second job, `ios-xcode`, configures the same tree with `-G Xcode` and builds every target for `-sdk iphoneos CODE_SIGNING_ALLOWED=NO`, then checks that each app embeds its extension with the generated plist and an iOS binary. pluginval opens every editor, the Synth's web page included, except on Linux; auval sees Gain's bypass property. ## Architecture

Public surface: `Lib/MakeASound/MakeASound.h` is the device library's umbrella public header, and `Lib/MakeASound/Plugin/MakeASoundPlugin.h` the plugin core's, which includes the first. Downstream code does `#include <MakeASound/MakeASound.h>`, a plugin `#include <MakeASound/Plugin/MakeASoundPlugin.h>`. The include root is `Lib/` (so the umbrella resolves as `<MakeASound/MakeASound.h>`); cross-module headers inside the library include each other by relative path.

Code under `Lib/MakeASound/` is grouped into domain folders, each compiled as separate TUs:

- **`Audio/`** — `Buffer` and `Channel`. `Buffer` is the one planar (channel-major) block type, **owning or referring**: constructed with a channel and sample count it owns zeroed storage; constructed over a `float* const*` table it refers to someone else's. Every access goes through that table plus a start offset, so `getSubBuffer(start, length)`, `getChannelSubset(first, count)` and `getSingleChannel(c)` are further `Buffer`s over the same table with no storage and no channel cap, and offsets compose. It is **move-only**: a copy is a compile error, `Buffer::copyOf` is the deep copy, `getSubBuffer(0)` the alias. `setSize` zeroes and never releases capacity; `referTo` drops owned storage. Constness lives in the reference — a `const Buffer` hands out `ConstChannel`s and cannot be sliced. `Channel` (`EA::Span<float>`) and `ConstChannel` are the single-channel currency used everywhere in place of a bare span. Sizes and indices are `int` throughout. Everything that does not allocate is `noexcept`; the allocating members are the owning constructor, `setSize` and `copyOf`, and `Tests/AllocationTests.cpp` pins that the rest stays off the heap.
  - `BusLayout.h`, `Playhead.h`, `ProcessContext.{h,cpp}` and `Processor.h` are the format-neutral processing vocabulary. `BusLayout` (`Bus {name, numChannels, isMain}`, `MidiBus {name}`, four vectors, `stereoInOut()` / `stereoOut()` / `instrument()`, `acceptsExactly`) is Miro-reflected; bus 0 on each side is the main one. `ProcessSpec {sampleRate, maxBlockSize, layout}` keeps rates `int` like `DeviceManager`; adapters round at their boundary. `ProcessContext` holds `Vector<Buffer>` inputs/outputs that **refer** to memory the host owns, `Vector<MIDI::Buffer>` in/out, a `Playhead` and an empty `ParameterChanges` placeholder; `clearMidi()` clears every MIDI buffer, `clearMidiOut()` the output half; `prepare(layout)` sizes the vectors and reserves every MIDI buffer, and the `main*()` accessors hand back bus 0 or a stand-in for an undeclared bus (an empty `Buffer`, a reserved `MIDI::Buffer` that reads empty) so code written against `mainOutput()` never indexes out of range. `Processor` is `getBusLayout()`, `prepare(const ProcessSpec&)`, `process(ProcessContext&) noexcept` and `reset() noexcept`; `reset` is a real virtual because Plug had to fake one in its AU adapter.

- **`Devices/`** — plain-data types and the audio façade.
  - `DeviceInfo.{h,cpp}` holds backend-independent structs/enums (`DeviceInfo`, `StreamConfig`, `StreamParameters`, `StreamOptions`, `Flags`, `AudioCallbackInfo`, `Error`, `AudioCallbackStatus`, `Callback`). No backend types leak in. `AudioCallbackInfo` is a copyable POD holding the backend's channel tables (`inputChannels`/`outputChannels`) and counts; `getOutput()` / `getInput()` build referring `Buffer`s over them per call, so `auto out = info.getOutput()` is free. It carries a `dirty` flag, raised when the stream shape (channels, sample rate, block size) changes since the previous callback — the signal for consumers to (re)allocate working buffers. Data structs opt into Miro JSON reflection in-place via `MIRO_REFLECT(...)`.
  - `DeviceManager.{h,cpp}` is the audio façade. It holds an `OwningPointer<MiniAudio::DeviceManager>` pimpl; the header forward-declares the backend type and the destructor is defined out-of-line in `.cpp` so the deleter sees the complete type. The `.cpp` is the only place that constructs the backend (`EA::makeOwned<MiniAudio::DeviceManager>()`).
  - `DeviceQueries.{h,cpp,mm}` plus `DeviceQueriesIOS.mm` is what the platform can say about a device without opening it: supported block sizes, its current sample rate, the route's own latency, the name the platform gives its own default device, and (iOS only) the route's native format. One TU per platform — Core Audio's HAL on macOS, `AVAudioSession` on iOS, conservative fallbacks elsewhere. The backend consults these where the platform's answer beats miniaudio's: `resolveDefaults` prefers the platform's default-device name because miniaudio marks several capture devices default on Core Audio, and `getStreamLatency` adds `getRouteLatency` to the periods it can see.
  - `AudioSession.{h,cpp}` plus one platform TU (`AudioSession-iOS.mm`, `AudioSession-Default.cpp`) is the platform audio session — `SessionCategory`, `SessionOptions`, `SessionConfig`, `SessionState`. Only iOS has one; elsewhere `hasAudioSession()` is false and the calls are no-ops. The backend applies it on **every** open (recovery's included) and it **follows the StreamConfig** where the app has not overridden it: category from whether there is an input side, preferred rate and block size from the config. miniaudio is initialised with `ma_ios_session_category_none` + `noAudioSessionActivate` so it never touches the session itself — preserve that when editing `initContext`. Interruptions and route changes need nothing of their own: on `InterruptionBegan` miniaudio stops the device, whose `Stopped` sends recovery to re-open (the session re-applied) every 250 ms until the session can activate again; a route change is `Rerouted` with the stream kept, and a media-services reset, which miniaudio does not observe, starves the callback until the watchdog recovers it. `InterruptionEnded`'s should-resume option is not consulted.
  - `Engine.{h,cpp}` runs a `Processor` on a `DeviceManager` stream with a `MidiManager`'s open inputs on its main MIDI bus: `prepare(processor, rate, block)` binds and prepares, `start(config, processor)` prepares then opens the stream (dropping the config's capture side when the layout has no input bus, so an instrument costs no microphone permission), and `process(AudioCallbackInfo&)` is the callback, public so a host with its own stream or a test can drive it. It owns the `ProcessContext`, the `MidiBlockSync` and two one-channel stand-ins: `silence` for an input bus channel the device cannot feed and a `bin` for an output bus channel it cannot play; a bus channel past a device that has *some* inputs reads device channel 0, so a mono mic spreads across a stereo bus. The main buses `referTo` the callback's tables through per-block pointer tables, nothing is copied, and device channels past the bus are cleared. A `dirty` block resets the processor and the MIDI window; one whose rate or block size differs from the spec re-prepares first, on the audio thread, the one documented allocation there. MIDI out buses are cleared and ignored here; the standalone format sends its plugin's MIDI out through `Standalone::MidiSender` instead (the header's comment still says it "arrives with the standalone format").

- **`MIDI/`** — MIDI types, the backend seam and the MIDI façade: `MIDI.{h,cpp}` (typed events + raw-byte conversion), `MidiInfo.{h,cpp}` (port info, event/message wrappers, `MidiNotification`), `MidiBlockSync.{h,cpp}` (aligns incoming MIDI to audio block boundaries), and `MidiManager.{h,cpp}` (façade with an `OwningPointer<MidiBackend>` pimpl, same out-of-line-destructor pattern). Nothing here names a backend.
  - `MidiBackend.h` is the abstract interface a platform implements, and the free `makeMidiBackend()` is what the façade constructs — defined in one TU per platform (`CoreMIDI/CoreMIDI-Factory.cpp` on Apple, `WinMIDI/WinMIDI-Factory.cpp` on Windows, `ALSA/ALSA-Factory.cpp` on Linux), selected in `Lib/CMakeLists.txt` the way `DeviceQueries` is. `MidiBackend` also carries the notification plumbing so every backend shares it: `notifyHost()` feeds both a `notificationCallback` delivered on the platform's MIDI thread and a mutex-guarded queue the host drains with `MidiManager::drainNotifications()` — the audio side's two-path design, same names.
  - `MidiPortRegistry.{h,cpp}` is `idForDevice`'s rule for MIDI: a port id is a slot keyed by the platform's stable identity (`kMIDIPropertyUniqueID` under Core MIDI, the device name plus its index under WinMM, the `client:port` pair under ALSA), not a position in the enumeration, so a hotplug does not renumber the other ports and a cached id keeps naming what it named. Backends scan through `beginScan()`/`idFor()` and resolve an id back to the current port number at open time. Virtual ports keep negative ids, which no registry hands out.
  - `MidiManager::now()` is the clock every backend stamps `MidiInputEvent::arrival` on, so `MidiBlockSync` compares like with like.
  - `MidiParser.{h,cpp}` is the platform-agnostic byte-stream parser (running status, interleaved realtime, bounded SysEx assembly into a buffer the owner hands in) that every native backend feeds raw packets into — pure and allocation-free, so it is covered by the allocation tests. `setIgnoredTypes(clock, activeSense)` reaches it through the façade, ports already open included.

- **`Plugin/`** — the `MakeASoundPlugin` target, with its own `CMakeLists.txt` (which finds eacp, adds `UI/`, `Web/`, `Standalone/`, `VST3/`, `AU/`, `AUv3/` and `Validation/` and includes `MakeASoundPlugin.cmake` and `MakeASoundWebEditor.cmake`): SDK-free, namespace `MakeASound`, nothing from a format SDK, and no eacp header included by any header: `Core/Editor.h` forward-declares `eacp::Graphics::View` and nothing more, so the target links no GUI tier. The only file in the directory itself is the umbrella `MakeASoundPlugin.h`; the code is in `Parameters/` (`Parameter`, `FloatParam`, `ChoiceParam`, `BoolParam`, `CommonParams`, `ParameterGroup`, `ParameterList`), `State/` (`StateContext`, `State`), `Core/` (`Description`, `Editor`, `HostEditListener`, `Plugin`, `StatePlugin`), `Host/` (`PluginWrapper`) and `Realtime/`. A plugin TU includes `<MakeASound/Plugin/MakeASoundPlugin.h>` and defines `describeModule()`.
  - **Parameters.** `Parameter` is the abstract base: range and default, `numSteps`, plain and normalized get/set, text in and out, and a state text form. The concrete ones are `FloatParam`, `ChoiceParam`, `BoolParam` and, in `CommonParams.h`, `DecibelParam`, `HzParam`, `TimeParam`, `PercentParam`; each takes a trailing `ParameterOptions` (`id`, `shortName`, `label`, `automatable`, `bypass`, `sessionOnly`, `hostId`) written with designated initialisers. Values are relaxed atomics read directly on the audio thread; a non-finite write is dropped. An id defaults to the name; `id` pins it so a rename keeps saved state and automation. A plugin declares its parameters in a `ParameterGroup` subclass (`ParameterGroup.{h,cpp}`) that registers members with the protected variadic `add(...)` in its constructor: parameters, groups, pointers to either (`OwningPointer`) and ranges of any of those (`std::array`, `EA::Array`, `std::vector`, `EA::Vector`), in declaration order, which is the automation order. A group takes `(name, GroupOptions {id, automatable})`; the root normally has no name, and a nameless group adds no segment to either path. It holds pointers to its members, so it neither copies nor moves, and `add` is constructor-time only. A duplicate id within one group (a nameless child shares its parent's key space) asserts. `forEach` walks the leaves depth-first with id path `"Osc 1/Attack"`, display path `"Osc 1 Attack"` and the AND of the leaf's and every enclosing group's `automatable`; `ParameterList` is built from a group through it, each `Entry` carrying `groups`, the named groups around it outermost first (`EnclosingGroup {id, name}`, the id an id path), which the AUv3 tree is built from; `bypassIndex()` is its first host-exposed entry whose parameter `isBypass()` (-1 with none; a second asserts and is ignored), and that entry's `Entry::bypass` is true, so a non-automatable bypass parameter is no bypass to a host. The host id is FNV-1a of the id path masked to 31 bits (`hostIdFor`), because VST3 reserves ids from 2^31 up, unless `ParameterOptions::hostId` names one, which must be below 2^31 too (asserted). Host ids are sorted for `indexOfHostId` and a collision asserts in debug. The list holds pointers into the group, which must outlive it. Parameters are not Miro fields: there is no `reflectValue` for `Parameter`, so one placed in a `MIRO_REFLECT` list is a compile error, pinned by a `static_assert` in `Tests/ParameterTests.cpp`.
  - **State.** `ParameterGroup::reflect` is the only way a parameter reaches a document: each leaf under its id, each named child group as a sub-object. A save writes a number, a choice's name or a bool; a load accepts any of the three (a choice by exact name, then case- and space-insensitively, or by index) and puts the parameter back to its default when its key is missing or means nothing, and a child group whose object is missing back to its defaults. A load assigns into the registered parameters and never rebuilds a container, so a vector of groups survives it. `StateContext` (`Preset`/`Session`) rides through Miro as the `CustomOptions` tag; a `sessionOnly` parameter is written and read only under `Session` and leaves no key otherwise. `State<ParamsT>` (`ParamsT` derives from `ParameterGroup`) is `version` plus `params`; a subclass reflects further members beside them. `version` is the schema this build writes and a load never changes it; the document's lands in `loadedVersion`, for migration code in a `reflect` override under `ref.isLoading()`. Loading is tolerant: a document with no `params` object, or no JSON at all, moves nothing. `loadParams` is the atomic half of a load, safe from any thread, and `deserializeExceptParams` the other half (a flag the base `reflect` checks before `ref["params"]`). Every non-parameter mutation ends in `markChanged()`, which the owner answers with `publish()` on the message thread; it publishes a preset and a session document, and `snapshotDocument(context)` is the published one with the parameters read live, which is how a host saves off the message thread without waiting on it (Plug's `auval -strict -stress` deadlock). `isPublishedDocumentCurrent` compares with `params` erased on both sides, since automation moves them between any two reads.
  - **`Plugin` and `StatePlugin`.** `Plugin : Processor` adds `name()` (pure), `format()` (set by the wrapper just after construction, so valid from `prepare` on, `Unknown` in the constructor), `acceptsLayout()` (default: `acceptsExactly` the declared layout), `latencySamples()`, `tailSamples()`, `takeLatencyChanged()`, the state hooks (`saveState`/`loadState` on the message thread, `saveStateWithoutMessageThread`, `isStateSnapshotCurrent`, `loadParameters`, and `loadStateExceptParameters`, whose default loads the whole document for a plugin that cannot split it), `parameters()` filled through the protected `setParameters`, and a `HostEditListener*` the adapter installs: begin/perform/end edit, an optional edit group, `latencyChanged` and `parameterInfoChanged`, message thread only, raised through `notifyHostLatencyChanged()`/`notifyHostParameterInfoChanged()`. `createEditor()` returns an `OwningPointer<Editor>`, null by default, and the host then shows `GenericEditor`; it is cheap by contract, since a host may call it only to learn whether one exists, so the view is built lazily. `StatePlugin<StateT>` owns a `State`, registers its parameters, routes every save and load through it and republishes on `markChanged`. Both documents are published, so a `StatePlugin` never marshals a save.
  - **`Description.h`**: `ModuleDescription {vendor, url, email, version, manufacturerCode, plugins}`, `PluginDescription {name, version, category, subcategory, pluginCode, create}`, `FourCC` and `Category {Effect, Instrument, MidiEffect}`. `ModuleDescription::version` is the AU bundle's `CFBundleVersion`, which macOS keys its component cache on, so it must move whenever the components do; `manufacturerCode` is the AU manufacturer and part of every VST3 class id, `pluginCode` the AU subtype. `describeModule()` is declared here and defined exactly once per binary, in the plugin's TU; for the tests that is `Tests/PluginTests.cpp`.
  - **`PluginWrapper`** owns the `Plugin` and its `ProcessContext` and is the per-block pipeline every adapter shares; an adapter translates its host's types into calls here and never calls the plugin's `process` itself. The constructor takes the `PluginFormat`. One block, in order: `setNormalizedParameter`/`setParameterByHostId`, `setPlayhead`, `clearMidi` + `pushMidiIn` + `sortMidiInByOffset` (stable), `bindInput` and `bindOutput` per bus, `process()`, then the adapter drains `midiOut()`. `bindOutput` decides per channel: a channel with a matching input channel gets a copy of it, or nothing when the host aliased the two, and a channel past the input's width is zeroed; per channel, because zeroing an output that aliases an input would wipe that input. `process()` clears MIDI out, runs the plugin under `ScopedNoDenormals` and then detaches every audio bus (zero channels, zero samples), so a bus the adapter does not bind next block reads empty instead of last block's host pointers. Every audio-thread member is `noexcept` and allocation-free, and an out-of-range bus or parameter index is a no-op; `pushMidiIn` on a full bus drops the event and returns false. `holdParameter`/`releaseParameter` count a plugin-side gesture, and while one is open `setNormalizedParameter`, `setParameter` and `setParameterByHostId` drop the host's write: the editor sets the `Parameter` directly and reports through `HostEditListener`. `saveState` on the message thread asks the plugin directly (asserting its snapshot is current); off it, it returns `saveStateWithoutMessageThread` and only marshals and waits when that is empty, with a throwing `saveState` handed back through the promise rather than hanging the caller. `loadState` applies `loadParameters` inline and `loadStateExceptParameters` on the message thread (inline when already there), so a host write landing in between survives. Each load takes a stamp from an atomic counter; the deferred half runs only if no later load was taken, and reaches the plugin through a `weak_ptr` so one queued past teardown drops. The wrapper must be destroyed on the message thread (asserted), where a running deferred load would otherwise hold a freed plugin. `ProcessContext::paramChanges` is still empty: adapters write parameters before the block.
  - **`Editor.h`**: `Editor` is what a plugin shows, one eacp view the standalone puts in its window and the VST3 and AU views embed: `view()` (an `eacp::Graphics::View&`, built on first call at the latest and stable for the editor's lifetime), `initialSize()` (`EditorSize`, 400×300 by default), `constraints()` (`EditorConstraints {resizable, minimum, maximum, aspectRatio}` in points, default not resizable, `{1, 1}` to `{16384, 16384}`, ratio `{0, 0}`, which locks nothing; only the ratio's proportion is read), and `onAttached()`/`onRemoved()` as the view goes into a window or comes out of one. `EditorConstraints::constrain(proposed)` (`Editor.cpp`) is the one rule every format applies: each side clamped, and with a ratio the proposal projected onto it, the minimum winning when bounds and ratio admit no size; every host opens the editor at `constrain(initialSize())`. `EditorHost` is whatever shows it (the standalone's window, a VST3 `PlugView`, the AU Cocoa view): `resizeEditor(EditorSize)` (true when the host took the size) and `drawsResizeHandle()`. Every format calls `setHost(this)` before `onAttached()` and `setHost(nullptr)` after `onRemoved()`, so `host()` is valid from `onAttached()` on; `canRequestResize()` is a host and `resizable`, and `requestResize(size)` constrains the size and hands it to the host, false when it cannot or the host refused. Non-copyable, message thread only. A plugin's editor may wrap a `WebView` (`Plugin/Web/`); the host-side UI never does.
  - **`Plugin/Realtime/`**: `MessageThread.{h,cpp}` is `isMessageThread()`, `callOnMessageThread()`, the reclaimer, and for a format loaded into a host `adoptHostMessageThread()` (marks the calling thread as eacp's main one when the code lives in a DLL, `eacp::Platform::isDLL()`; a no-op in an executable, idempotent) and its inverse `releaseHostMessageThread()` (eacp's `detachCurrentThreadAsMain`: the message-only window and its class, the deferred-call scheduler thread and the queued calls go, for the module's exit before the host unloads it), `messageLoopFd()` and `pumpMessageLoop()` (the descriptor a host run loop watches and one non-blocking pass of eacp's loop, defined in `MessageThread-Linux.cpp`; `MessageThread-Default.cpp` answers -1 and does nothing, and `Plugin/CMakeLists.txt` picks one), and the `MessageThread*.cpp` TUs are the only ones in `MakeASound` or `MakeASoundPlugin` that include eacp. `RealtimeSwap<T>` hands a heavy object from the message thread to the audio thread with two atomic slots: `publish(args...)` builds one into `pending` (freeing any the audio thread never took), `currentForBlock()` takes it and moves the old one into `retired`, and a process-wide reclaimer sweeps every registered swap's `retired` on the message thread every 250 ms. Ownership is single, no `use_count`: while `retired` is still full the audio thread keeps its object one more block, so the latest publish is delayed, never lost. Construct, publish and destroy off the audio thread, and destroy only once it has stopped.
  - **`Plugin/UI/`** — the `MakeASoundPluginUI` target (links `MakeASoundPlugin` and `eacp-ui` PUBLIC), the eacp-ui pieces every format shares, so VST3's and AU's views link it without the standalone's device and window code. Host-side UI here and in `Plugin/Standalone/` is eacp-ui GPU widgets in `eacp::UI::ComponentHost` trees, not web pages: no npm, no JS bridge, no embedded resources. `GenericEditor` is the `Editor` a host shows when `createEditor()` returns null: one row per entry of `parameters()`, its display name, a control by type (`ComboBox` for a `ChoiceParam`, `Checkbox` for a `BoolParam`, otherwise a `Slider` in normalized units, its default the parameter's, its thumb following a stepped parameter's snap) and `valueToText` of the value, in a `ScrollPanel`, 420 wide and 32 per row clamped to 96..720 high; its `constraints()` are resizable from 320×96 to 1200×1200 at any ratio, since the rows scroll. The view is built on the first `view()`; while attached a 30 Hz timer pulls every value, touching a widget only when its value moved and never the one being dragged. Edits write the `Parameter` directly and report begin/perform/end through the plugin's `HostEditListener` when there is one (a combo or checkbox change is a whole gesture). `onAttached()` shows a `ResizeGrip` when `ResizeGrip::isWantedBy(editor)` (it can request a resize and its host does not draw a handle, which today is the AU view alone), `onRemoved()` hides it. `ResizeGrip` (`ResizeGrip.{h,cpp}`) is Plug's bottom-right handle, an 18-point eacp view an editor adds as its view's last child at `cornerOf(bounds)`: two-tone diagonals, drawn and hit-testable only while `canRequestResize()`, and a drag asks `requestResize` for the parent's size at `mouseDown` plus the pointer's travel since, never accumulating requests, so a host that answers differently does not make it drift. Message thread only.
  - **`Plugin/Web/`** — the `MakeASoundPluginWeb` target (`ParameterApi.cpp`, `WebEditor.cpp`; links `MakeASoundPluginUI` and `eacp-webview` PUBLIC), built where both exist, which is where eacp has a native web runtime (macOS, iOS, Windows), skipped with a status line elsewhere; namespace `MakeASound::Web`. `ParameterApi` is the Miro API a page drives the parameters through, by id: commands `getParameters()` (`WebParameters`, a list of `WebParameter {id, name, label, normalized, text, steps, choices, automatable}`), `beginEdit`/`endEdit(WebParameterId)` and `edit(WebParameterEdit {id, normalized})`, event `values` (`WebParameterValues {changed}`), each list and bare id inside a reflected struct because Miro's TypeScript codegen emits broken types for a bare `Vector` or string argument. Message thread only.

    - `StandaloneHost` (`StandaloneHost.{h,cpp}`) is the standalone with no window, and a public API: an app of a plugin's own includes `<MakeASound/Plugin/Standalone/MakeASoundStandalone.h>` (the plugin umbrella, `StandaloneHost`, `SettingsPanel`, `EditorWindow`, `TypingKeyboard` and `GenericEditor`, never `StandaloneApp`), code with no window `StandaloneHost.h` alone over `MakeASoundStandaloneCore`; the app holds the host as its first member and its UI after, and calls `start()`. Members, in construction order: `deviceManager`, `midiManager`, `sender`, `pluginWrapper` (`PluginFormat::Standalone`, no `HostEditListener`, since there is no host), `processor`, `audioEngine`, the settings path, the default `Preset` document, the fallback config, the open MIDI output's id and the settings read at construction.     - `StandaloneApp` is the default app, run by `eacp::Apps::run<StandaloneApp>()` from `StandaloneMain.cpp`: `host` (a default `StandaloneHost`) and then `shell`, a pimpl `Shell` each platform defines in its own TU with the constructor and destructor, which call `host.start()` and then build the shell. `StandaloneApp.cpp` holds what both share: `createEditor` (`createEditor()` or `GenericEditor`), `connectSettings` (the panel's callbacks go to the host and it is told back what the host settled on) and `resetAudioAndMidi`.

  - **`Plugin/VST3/`** — the `MakeASoundVST3` target (links `MakeASoundPlugin` and `vst3sdk` PUBLIC, and with the view `MakeASoundPluginUI` and `eacp-graphics` PRIVATE), namespace `MakeASound::VST3`.     - `Adapter` is the one class per plugin: `Vst::SingleComponentEffect` (component, processor and controller in one object) plus `IMidiMapping` and `HostEditListener`, owning a `PluginWrapper` built with `PluginFormat::VST3` and driving it in the documented order, never calling the plugin's `process`. Latency changes reach `restartComponent(kLatencyChanged)` through a compare-exchange on the last figure the host fetched, on the message thread.
    - **State** is one document through `IComponent::getState`/`setState` and the wrapper's `saveState`/`loadState`: a `Session` unless the stream's `IStreamAttributes` names a state type other than `kProject` (then a `Preset`); the controller's `getState`/`setState` stay `kNotImplemented` and `setComponentState` reads nothing. No exception crosses the ABI.
    - **MIDI CC** arrives through `IMidiMapping` onto hidden shadow parameters, registered whenever the layout has a MIDI input bus: 16 channels × 131 controllers (CC 0–127, aftertouch, pitch bend, program change) per bus for up to 16 buses, id `0x7FFF0000 | bus << 12 | channel << 8 | controller`, below 2^31; queue points become `MIDI::Event`s at their offsets (`Conversion.{h,cpp}`). A plugin parameter whose host id lands in that range wins, and a debug build asserts on it. Notes, poly pressure, SysEx and legacy CC events convert both ways.
    - `Factory.{h,cpp}`: `makeFactory(module)` is a `CPluginFactory` listing every plugin, class id `FUID(manufacturerCode, pluginCode, FourCC("VST3"), 0)` (Plug's derivation, so a plugin moved from Plug is the same class to a DAW; never change it once shipped), no `kDistributable` flag. `EntryPoint.cpp` (`GetPluginFactory` over `Steinberg::gPluginFactory`) is compiled into each module, never into the static target. The factory's create function and `initialize` both call `adoptHostMessageThread()`, and `EntryPoint.cpp` registers a `Steinberg::ModuleTerminator` that calls `releaseHostMessageThread()` from `ExitDll`/`bundleExit`/`ModuleExit`: a host scans a plugin, unloads the module and loads it again for the first instance, and eacp's message-only window (its procedure in our image) would otherwise outlive the code it dispatches into, which is how pluginval crashed on Windows at "Open plugin (cold)".
    - **The view.** `createPlugView(owner, plugin)` (`PlugViewFactory.h`) is defined twice, by `PlugView.cpp` where the UI tier exists and by `NoPlugView.cpp` (null) where it does not, the choice made inside the target at link time rather than by a registering initialiser. `PlugView` is a `CPluginView` + `IPlugViewContentScaleSupport` over `eacp::Graphics::EmbeddedView` showing `createEditor()` or `GenericEditor`, holding an `IPtr` to the adapter so the plugin outlives it. The editor lives as long as the view; the embedding only between `attached` and `removed`, with `onAttached()`/`onRemoved()` around it. Platform types: `NSView`, `HWND`, `X11EmbedWindowID`. A `ViewRect` is in points on macOS and in pixels (points × the host's content scale) elsewhere; `getSize` reports `constrain(initialSize())` until the host sizes the view, `canResize` is `constraints().resizable`, `checkSizeConstraint` converts the host's rect to points through `rectScale()`, constrains it and writes it back (the base class's answer for a fixed editor), and key events are left to eacp's own view. `PlugView` is the editor's `EditorHost` from construction to destruction: `resizeEditor` hands the rect to `IPlugFrame::resizeView` (false with no frame or a refusal) and, since the SDK lets an accepting host skip `onSize` when it judges the size unchanged, applies it through `onSize` itself when no `onSize` arrived during the call (a counter, as JUCE does); `drawsResizeHandle()` is true, so no grip is drawn.
    - **The host's run loop.** `HostRunLoop.h` is `attachHostRunLoop(FUnknown*)`, an owned `HostRunLoop` that pumps the message loop for as long as it lives, or null when the context offers no run loop. `HostRunLoop-Linux.cpp` registers an `IEventHandler` for `messageLoopFd()` with the host's `IRunLoop` and calls `pumpMessageLoop()` when it is readable; `HostRunLoop-Default.cpp` always returns null.     - **Platform code is split by TU, as eacp does, never by `#if`**: `PlugView-{macOS,Windows,Linux}.cpp` define `PlugView::nativeViewType()` (the type `attached()` accepts: `NSView`, `HWND`, X11 window id), `rectScale()` (1 on macOS, where a `ViewRect` is in points; the content scale elsewhere, where it is in pixels) and `applyContentScale()` (`setPixelsPerPoint` off macOS, nothing on it), and `Plugin/VST3/CMakeLists.txt` compiles one of each pair.
  - **`Plugin/AU/`** — three targets. `MakeASoundAUDescribe` (`ComponentType.cpp`, `HostParameters.cpp`, `Plist.cpp` and `ViewPlacement.cpp`, linking `MakeASoundPlugin`, AudioToolbox and CoreFoundation PUBLIC, C++20, SDK-free) is built on every Apple platform, iOS included, since the AUv3 adapter shares it; the other two, macOS only, when `TARGET ausdk`. It is what the plist writers and both factories ask: `componentInfoFor(module, plugin)` constructs the plugin once to read its layout (so a plugin constructor must be safe in a CLI) and answers type, subtype (`pluginCode`), manufacturer (`manufacturerCode`) and bus counts, the type being `aumu` for `Category::Instrument`, `aumi` for `MidiEffect`, `aumf` for an effect with a MIDI input bus and `aufx` otherwise; `findPlugin(module, subtype)`, `fourCCString`, `componentTag(category)` (an app extension's `tags`: `Synthesizer`, `MIDI` or `Effects`) and `versionNumber` (`"major.minor.patch"` as `major << 16 | minor << 8 | patch`, each part clamped, a bad one 0). `MakeASoundAU` (`Adapter`, `Conversion`, `State`; links `MakeASoundPlugin`, `MakeASoundAUDescribe` and `ausdk` PUBLIC, so C++23, unity under `MAKEASOUND_UNITY_BUILD`) is the format, namespace `MakeASound::AU`. Every adapter TU includes `AUCommon.h` (the SDK's `AUMIDIEffectBase.h` and `MusicDeviceBase.h`, `au` as an alias of `ausdk`); the SDK's `AUSDK_RTSAFE` overrides are matched with plain `noexcept override`.
    - `Adapter` is the one class every plugin ships as: `au::MusicDeviceBase` (`AUMIDIBase` over `AUBase`, so one class answers the effect, music-effect, instrument and MIDI-processor selectors) plus `HostEditListener`, owning a `PluginWrapper` built with `PluginFormat::AU` and driving it in the documented order, never calling the plugin's `process`. It finds its plugin through `AudioComponentGetDescription` on its own component, `describe(subtype)` over a function-local `describeModule()`, so several plugins share one bundle; a subtype naming none throws `kAudioUnitErr_InvalidProperty`, which the SDK's `Open` turns into a failed instantiation.
    - **The factory.** `EntryPoint.cpp` is compiled into each module, never into the static target, and defines the module's two exported symbols. `MakeASoundAUFactory`, the one every `AudioComponents` entry names, calls `adoptHostMessageThread()`, returns null for a foreign manufacturer or an unknown subtype, and dispatches on `componentType` to `AUMusicDeviceFactory` (`aumu`), `AUMIDIEffectFactory` (`aumf`, `aumi`) or `AUBaseFactory` (`aufx`) over `Adapter`, so each type gets its own dispatch table. The constructor adopts the message thread too. Nothing releases it: AU has no module-exit hook, and on macOS releasing only stops eacp's `callAfter` scheduler, whose own static destructor already does that when the image is finalized. An `__attribute__((destructor))` function cannot do it instead, since dyld registers one when the image loads and so runs it after the image's function-local statics are gone: once `RealtimeSwap`'s reclaimer had started the scheduler, auval aborted at exit locking its destroyed mutex.
    - **Parameters.** An `AudioUnitParameterID` is the parameter's 31-bit host id, looked up with `indexOfHostId`, so `Globals()` runs in map mode; `PostConstructor` writes every exposed id with the plugin's value, so no `SetParameterRT` ever inserts on the render thread, and `SetParameter` is overridden to refuse a global id that is not exposed (`kAudioUnitErr_InvalidParameter`), so the SDK's map never grows behind it. Only `isHostExposed` entries exist to the host: `GetParameterList` returns them in declaration order, `GetParameterInfo` on another id is `kAudioUnitErr_InvalidParameter`, and `HostParameters.{h,cpp}` fills the info (CF name, plain range and default, unit `Boolean` for a bool, `Indexed` for a stepped parameter, `Generic` otherwise, flags readable, writable, `HasCFNameString` and `CFNameRelease` on every one, `ValuesHaveStrings` only on a stepped choice or bool, the ones that answer `GetParameterValueStrings`), the value strings for those, and `kAudioUnitProperty_ParameterStringFromValue`/`ParameterValueFromString` through `valueToText`/`textToValue` (clamped, and the current value when the text yields a non-finite number), so a skewed parameter reads right. `CanScheduleParameters()` is false, since true makes the SDK `push_back` on the render thread: a host write lands in `Globals()` and, unless a gesture holds the parameter, in the wrapper at once, so a save between the write and the render it lands in never has to choose between the host's value and one the plugin moved itself; on the message thread `SetParameter` also checks the latency, as the VST3 adapter's `setParamNormalized` does.
    - **Reconciliation** is the top of each render, per exposed entry, against two baselines, `lastHostValue` (what `Globals()` held) and `lastPluginValue` (what the plugin held) at the end of the last block. A host value that moved, on a parameter no gesture holds, goes to the plugin through `setParameter`, and both baselines take the result. Otherwise `Globals()` is written back only when the plugin moved on its own or a held parameter's host write must be undone, and then only if it differs. A host value is therefore never overwritten by the plugin's snapped form of it: auval's "Parameter did not retain set value when Initialized" sets off-grid values a stepped parameter snaps and reads them back. `Initialize` pushes `Globals()` into the plugin and seeds both baselines.
    - **Gestures** from the editor go out through `AUEventListenerNotify`: begin (`holdParameter` first), a value change after `Globals()->SetParameter` with the plugin's plain value, end (`releaseParameter` last), only for an exposed parameter; edit groups are no-ops. `parameterInfoChanged` posts `PropertyChanged` for `ParameterList` and `ParameterInfo`.
    - **Buses and formats.** `PostConstructor` sets every element to float32 non-interleaved at the declared count and `SetWillAllocateBuffer(true)` on the outputs. The constructor publishes, through `SupportedNumChannels`, the pairs `acceptsLayout` accepts for main-bus counts 1..8 on each side (0 for a side with no bus), from a member vector that outlives the call. A stream format is writable only before `Initialize`, and `ValidFormat` judges an element alone, since hosts set one at a time: main-bus counts must appear on that side of some published pair, other buses must match the declared count. `Initialize` builds the layout from each element's `NumberChannels()` and runs it through `PluginWrapper::setLayout` (`kAudioUnitErr_FormatNotSupported` when refused), prepares at `Output(0)`'s rate (rounded) and `GetMaxFramesPerSlice()`, sizes the per-bus channel-pointer tables and the 16 KiB MIDI packet buffer (only with a MIDI-out bus), and resets. Buffer pointers are taken per render, never in `Initialize`, because `DoInitialize` reallocates after it.
    - **Render** overrides `Render`, not `ProcessBufferLists`. In order: a pending reset (`wrapper.reset()`), `clearMidi()` and the hand-over of the MIDI staged since the last block onto MIDI-in bus 0 under its spin lock, reconcile parameters, `PullInput` per input bus (one that fails binds empty, one with fewer buffers than channels binds what it has and is not used as a matching input), `setPlayhead` from `CallHostBeatAndTempo`, `CallHostMusicalTimeLocation` and `CallHostTransportState` (`Conversion.{h,cpp}`; the sample time is the transport's `sampleInTimeline`, as VST3 reports `projectTimeSamples`, and the timestamp's `mSampleTime` only when the host has no transport callback; `isValid` when any answered), `sortMidiInByOffset`, bind each output with the input of the same index as the matching input when it was fully bound with the same count, `process()` and MIDI out. Outputs follow `AUBase::DoRenderBus`: with one output element bus 0 is `GetBufferList()`, which the SDK already pointed at the host's buffers or prepared; with more, the SDK renders every bus into its own buffers and copies each out when its bus is rendered, so every bus, bus 0 included, is `PrepareBuffer(frames)`, and a host rendering bus 1 first still finds bus 0 written. `DoRender` already refuses an uninitialized unit and too many frames, and disables denormals itself.
    - **Reset** is a real one: `Reset()` raises an atomic flag and calls the base, and the next render runs `wrapper.reset()`, since the SDK does not serialise `Reset` against `Render`. No CC 120 is injected.
    - **MIDI in.** `HandleNoteOn`, `HandleNoteOff` (the SDK already turns a zero-velocity note on into one), `HandleControlChange`, `HandlePitchWheel` (14-bit, normalized), `HandleChannelPressure`, `HandlePolyPressure`, `HandleProgramChange` and `HandleSysEx` (dropped past `MIDI::SysEx::maxBytes`) stage their event at its frame, and `HandleNonNoteEvent` puts CC 120, 121 and 123 back on the control-change path and stages a program change itself, because `AUMIDIBase` diverts all four to handlers with no frame. `MusicDeviceMIDIEvent` may come from a host thread other than the render thread, so, as in JUCE's wrapper, staging is a `MIDI::Buffer` of the adapter's (1024 events, reserved in `PostConstructor`, a full one dropping the event) under a `SpinLock`, which `Render` empties into the wrapper at the top of the block. AU delivers one MIDI stream, so every event lands on MIDI-in bus 0 and no other MIDI-in bus is ever fed. `MIDIEventList` stays at the SDK default, so a host falls back to `MIDIEvent`.
    - **MIDI out**, with a MIDI-out bus only: `kAudioUnitProperty_MIDIOutputCallbackInfo` (a `CFArray` of bus names) and the writable `kAudioUnitProperty_MIDIOutputCallback`, published to the render thread through a `RealtimeSwap` (`publish` in `SetProperty`, `currentForBlock()` once per render). Each render fills a `MIDIPacketList` in the buffer sized at `Initialize`, one packet per event stamped with its sample offset, flushing to the callback when full, and calls it per non-empty bus with the render timestamp.
    - **State** is the SDK's ClassInfo dictionary plus one key, `MakeASoundState`, a `CFData` of the wrapper's `Session` document (`State.{h,cpp}`), restored through `kAudioUnitProperty_ClassInfo` or `kAudioUnitProperty_ClassInfoFromDocument`, which the SDK does not dispatch and Logic uses for a document, so `GetPropertyInfo` answers it (writable, `sizeof(CFPropertyListRef)`) and `SetProperty` routes it to `RestoreState`. Both paths, and every save, are `Session`: AU gives no reliable preset signal on a save. `SaveState` reads the wrapper, which `SetParameter` already wrote, so a host write no render has consumed yet is in the document and a value the plugin moved itself is not undone. `RestoreState` runs the base (which checks the codes and restores `Globals()`), then loads the document and mirrors the plugin's values into `Globals()`, or with no document pushes the restored `Globals()` into the plugin, and checks the latency. No exception crosses the ABI. Off the message thread the wrapper's save reads the published snapshot, which is why `auval -strict -stress` does not hang here as it did in Plug.
    - **Latency and tail.** `GetLatency()` is `latencySamples()` over the output rate and records the figure; a change, from `latencyChanged`, a parameter edit or a restore, posts `PropertyChanged(kAudioUnitProperty_Latency)` on the calling thread, through a compare-exchange on the last fetched figure so only the caller that moves it notifies (`takeLatencyChanged` is consumed on the message thread only). `SupportsTail()` is true and `GetTailTime()` is `tailSamples()` over the rate. **Bypass:** `kAudioUnitProperty_BypassEffect` (global, a writable `UInt32`) is answered only for a plugin with a `bypassIndex()`, and refused otherwise. Reading it is the bypass parameter's normalized value ≥ 0.5; writing goes through `MusicDeviceBase::SetParameter` on its host id and then the wrapper, so a gesture holding the parameter drops it, and reaches an `AUEventListener` as a value change, the SDK posting the property once `SetProperty` succeeds. - **`MiniAudio/`**, **`CoreMIDI/`**, **`WinMIDI/`** and **`ALSA/`** — the backends (namespaces `MakeASound::MiniAudio`, `MakeASound::CoreMIDI`, `MakeASound::WinMIDI` and `MakeASound::ALSA`). Each has a `*-Backend.{h,cpp}` of pure conversion functions and a `*Manager.{h,cpp}` that owns the handle. `MiniAudio::DeviceManager` owns the `ma_device` and the `audioCallback` trampoline that miniaudio invokes; it **de-interleaves** the incoming/outgoing interleaved buffers into two owning `Buffer` scratches, sized at open for the negotiated block, and re-interleaves on the way out (so callers only ever see planar data). miniaudio is the only third-party library left behind either façade; every MIDI backend is the platform's own API.
  - `CoreMIDI::MidiManager` is the Apple MIDI backend. It holds the `MIDIClientRef`, one shared input port that every opened source connects to, one output port, and a per-open-port `InputPort` carrying its `MidiParser`, its SysEx assembly buffer and its `SPSCQueue`. Raw MIDI 1.0 bytes only: `MIDIPacketList` in and out (`MIDIInputPortCreateWithBlock`, `MIDISend`, `MIDIReceived`), so the wire stream reaches `MidiParser` as it arrived rather than through a UMP round trip.
  - **Run-loop thread.** Core MIDI delivers notifications on the run loop that was current when the *process* created its first MIDI client, and keeps that pin after the thread dies. So `NotifyLoop` is a process-wide singleton thread, started on first use and never stopped, on which every client is created, used and disposed — hotplug then works in a CLI with no run loop of its own, and a manager built after an earlier one died still hears it. Where another library got its client in first the pin is theirs; both notification paths still carry whatever arrives.
  - `WinMIDI::MidiManager` is the Windows MIDI backend. One `HMIDIIN` per open input with a `CALLBACK_FUNCTION` callback, one `HMIDIOUT`, and the same per-port `InputPort` (`MidiParser`, assembly buffer, `SPSCQueue`) the Apple one has. Short messages arrive packed into `MIM_DATA`'s dword and are unpacked by status length; a dump arrives through a ring of four 1 KiB `MIDIHDR`s, re-armed with `midiInAddBuffer` from inside the callback — the one WinMM call allowed there. A header handed back empty is `midiInReset` on the way out, not data, so it is not re-armed. Names carry the port index appended, and that name is the whole identity WinMM offers.
  - **No loop thread on Windows.** WinMM has no virtual ports, no hotplug notification and no thread of ours to sweep on, so `openVirtual*` refuse, `PortAdded`/`PortRemoved` are diffed out of each `getInputPorts()`/`getOutputPorts()` against the previous scan, and the receive thread's `QueueOverflow`/`SysExDropped` flags are swept there too — not in `drainMessages()`, which is the audio thread's and `notifyHost` locks. Timestamps are `MIM_DATA`'s milliseconds since `midiInStart` added to a `steady_clock` reading taken at that call, so 1 ms is the resolution of every arrival. Output SysEx goes out through `midiOutPrepareHeader`/`midiOutLongMsg` on a staging buffer sized at open, and `midiOutUnprepareHeader` is the wait that keeps `sendMessage` synchronous.
  - **Two SysEx tiers.** Callback mode delivers a dump of any size up to the port's assembly buffer (`MidiManager::setMaxSysExBytes`, default 64 KiB, allocated at open, never on the MIDI thread); queue mode delivers one only when it fits `MIDI::SysEx::maxBytes` (32). Either drop raises `SysExDropped`. Queue mode hands events over through a per-port `SPSCQueue<MidiInputEvent, 2048>`; a full queue drops the event and raises `QueueOverflow`. Both notifications are raised from a flag the receive thread sets and the run loop sweeps, because `notifyHost` takes a mutex and the MIDI thread may not.
  - `ALSA::MidiManager` is the Linux MIDI backend. One sequencer client (`snd_seq_open`, duplex) with one application input port every subscription lands on and one output port every send leaves by; **opening a port is a subscription** (`snd_seq_connect_from` / `snd_seq_connect_to`), and a **virtual port** is a port of our own — `WRITE|SUBS_WRITE` for a virtual input, `READ|SUBS_READ` for a virtual output — which is why the loopback the tests use is the same on Linux as on Apple. Enumeration walks `snd_seq_query_next_client`/`_port`, naming a port `"<client>:<port> <client num>:<port num>"` and skipping the system client and our own two plumbing ports but not our virtual ones. An event routes to its `InputPort` by `dest.port` when it is a virtual one of ours and by `source` when it came through the shared input port; its bytes reach `MidiParser` raw (a `SND_SEQ_EVENT_SYSEX` fragment as it is, anything else through `snd_midi_event_decode`), so the SysEx tiers and the ignored types are identical to Core MIDI's.
  - **Input thread.** One per manager, blocking in `poll` over `snd_seq_poll_descriptors` plus an `eventfd`, with `snd_seq_event_input_pending(seq, 1)` guarding every `snd_seq_event_input` so a blocking handle never blocks it. It takes no lock and no heap: the open-port list belongs to it, and the host **parks** it (a write to the `eventfd`, an acknowledgement through two atomics) before opening or closing anything, which costs the thread one relaxed load per wake-up. `PortAdded`/`PortRemoved` come from `SND_SEQ_EVENT_PORT_START`/`PORT_EXIT` on the system announce port, pushed into an `SPSCQueue` that a small sweeper thread turns into notifications every 100 ms alongside the dropped/overflow flags — the run loop's job on Apple. The poll timeout is also what ticks the parser's SysEx timeout when a dump stalls.
  - **Timestamps and sends.** A realtime sequencer queue timestamps every input port, and the offset between its clock and `steady_clock` is taken once when the queue starts, so `MidiInputEvent::arrival` is the kernel's stamp on `MidiManager::now()`'s clock; an unstamped event falls back to now. Sends go out through `snd_seq_event_output` + `snd_seq_drain_output` rather than `snd_seq_event_output_direct`, which grows a scratch buffer of its own the first time it is handed a variable-length event; a dump leaves as a run of ≤512-byte SysEx fragments pointing straight at the caller's bytes, so a send of any size is synchronous and allocation-free.

**Default configs:** there is no `getDefaultConfig()` — `getDefaultOutputConfig()` / `getDefaultInputConfig()` / `getDefaultDuplexConfig()` make the direction explicit, because a config that claims an unwanted capture side costs the app a microphone permission on macOS and iOS. `pickCompatibleSampleRate` prefers a device's `currentSampleRate` over its `preferredSampleRate`: re-clocking a shared device moves it under every other app, and asking for a rate it is not on leaves the backend resampling.

**Adding a new file/module:** create `Lib/MakeASound/<Folder>/<Name>.{h,cpp}` (reuse an existing domain folder where it fits) and add `MakeASound/<Folder>/<Name>.cpp` to the source list in `Lib/CMakeLists.txt`. Include siblings in the same folder as `"<Name>.h"` and headers in other folders as `"../<Folder>/<Name>.h"`.

**Device ids:** an id is a slot in a name-keyed registry (`idForDevice`), not a position in the enumeration, so a hotplug does not renumber every device after the one that moved and a cached `DeviceInfo::id` keeps naming what it named. The registry is per-API and `setBackend` clears it.

**Notifications:** every one goes down two paths — `notificationCallback`, delivered immediately on whatever OS thread raised it, and a mutex-guarded queue the host drains with `DeviceManager::drainNotifications()` on its own thread. Keep both fed from `notifyHost`; the queue is what lets a UI react without writing its own marshalling.

**Callback status:** miniaudio's data callback carries no status, so `AudioCallbackStatus` is measured from the callback clock (`getCallbackStatus`): a block arriving more than a period late past a small margin missed its deadline. Keep `lastCallbackUs` in microseconds — the watchdog and this share it, and millisecond resolution is too coarse at small block sizes.

**Dirty-flag flow:** `DeviceManager::openStream` wraps the user callback in a lambda that compares the incoming `AudioCallbackInfo` against `prevInfo` (via the struct's `operator==` on channels/sampleRate/maxBlockSize) and sets `info.dirty = true` on change. Preserve this wrapping when editing `openStream` — the raw backend callback does not set `dirty`.

**Failure handling:** neither the audio path nor the MIDI one throws. `DeviceManager::start`/`setConfig` return an `Error`, and `isRunning()`/`getLastError()` say what happened; `getErrorMessage(Error)` turns one into something a user can read. A machine with no device, or with one that is busy, is an ordinary desktop state — `getDefaultConfig()` leaves a side unset when the machine has nothing of that kind (asking for duplex on a mic-less box fails the whole open), and the miniaudio backend maps every `ma_result` through `getError` instead of raising. Keep new backend code on that path: the recovery worker drives opens from its own thread, where an exception has nowhere to go. The MIDI façade returns `Error` too, and no MIDI backend throws: an `OSStatus`, an `MMRESULT` and a negative errno each go through their backend's `getError`. `ALSA::MidiManager` maps every negative errno through `getError` and silences alsa-lib's own stderr hook (`snd_lib_error_set_handler`) for the length of its open, because a machine with no `/dev/snd/seq` is an ordinary state: `isAvailable()` is false, nothing is printed and every call is a no-op.

**Allocation tests:** `Tests/AllocationTests.cpp` and `Tests/RealtimeThreadAllocationTests.cpp` assert that the real-time paths never reach the allocator, through the shared harness in `Tests/AllocationProbe.h`. The ban is thread-local and covers `free` as well as `malloc`, so what is measured is heap *activity*, not growth. The pure paths are called under a `ScopedSetter`; the threads we don't own (a live audio callback, the platform's MIDI thread — Core MIDI's receive thread on Apple, the ALSA backend's own input thread on Linux) raise and lower the ban from inside their own callbacks and report through an atomic — `ThreadProbe::mark()` runs at the end of the callback, so the window it opens covers that block's tail plus all of the next one. Interposition needs `dlsym(RTLD_NEXT, ...)`, so both files (and the `AllocationsChecker` link) are added to the test target only on Apple and Linux — the condition lives in `Tests/CMakeLists.txt`, not in the sources, and a suite that reports zero because nothing was watching is worse than no suite. Anything new on the audio thread or on the platform's MIDI thread belongs here — the allocations these caught were a `MidiMessage` built and destroyed per delivered message on the way out of a port (now a per-port buffer the callback borrows), `MIDI::Buffer::addFrom` reserving the source's size instead of the merged one, and alsa-lib's `snd_seq_event_output_direct` growing a scratch buffer for a variable-length event (now `snd_seq_event_output` + drain).

`Tests/PluginAllocationTests.cpp` pins the plugin core the same way: parameter value I/O, host-id lookup, `RealtimeSwap::currentForBlock`, and a whole `PluginWrapper` block driven as an adapter drives it, for an effect and an instrument, in place and not. It is added only when the allocation suites and `MAKEASOUND_BUILD_PLUGIN` both are, so a case that needs the plugin core goes there and never into `AllocationTests.cpp`, which must build without it (that file gained the `Smoother` steps, which live in the device library). `Tests/StandaloneAllocationTests.cpp`, added when `MakeASoundStandaloneCore` is a target, drives a `StandaloneProcessor` block on `Engine` for the effect, and for the instrument with an injected note echoed through MIDI out into the `MidiSender`, and runs the effect on the real default output device through `Engine::start`, the ban raised from inside the plugin's `process` by a `ThreadProbe` (declared first, since the audio thread still carries the ban on its way down) and nothing measured where no device opens or it barely calls back.

**Serialization:** Miro provides reflection natively for primitives, integrals, `std::vector`/`std::array`/`std::map`/`std::optional`, and enums (string-named via `Miro::enumToString`). ## Conventions

- C++20, namespace `MakeASound`; backend code in `MakeASound::MiniAudio`, `MakeASound::CoreMIDI`, `MakeASound::WinMIDI` and `MakeASound::ALSA`, format code in `MakeASound::Standalone`, `MakeASound::VST3`, `MakeASound::AU` and `MakeASound::AUv3`. The one exception to C++20 is whatever links `ausdk`, whose headers need C++23.
- `.clang-format`: Allman braces, 4-space indent, 85-col limit, pointer-left, no tabs, `NamespaceIndentation: None`, `SortIncludes: false` (include order is intentional — don't reorder).
- The `MakeASound` CMake target is a `STATIC` library; sources are listed individually in `Lib/CMakeLists.txt`. It links `Miro` PUBLIC (Miro headers leak through the public data structs) and `miniaudio` PRIVATE, plus whichever MIDI library the platform selected — the Core MIDI frameworks on Apple, `winmm` on Windows, `ALSA::ALSA` + `Threads::Threads` on Linux (every backend is fully hidden behind the façades).
- `MakeASoundPlugin` is a second `STATIC` target, defined in `Lib/MakeASound/Plugin/CMakeLists.txt`, which `Lib/CMakeLists.txt` adds under `MAKEASOUND_BUILD_PLUGIN`. It links `MakeASound` PUBLIC and `eacp-core` PRIVATE. eacp stays inside the `Plugin/Realtime/MessageThread*.cpp` TUs, and no header includes one of eacp's (`Editor.h` forward-declares the view), and no format SDK ever enters the target: an adapter links its SDK on top.
- `MakeASoundDSP` (`DSP/`, linking `MakeASound` PUBLIC) is a `STATIC` target in its own directory's `CMakeLists.txt`, always built, never linked by the library itself.
- `MakeASoundStandaloneCore` (`Plugin/Standalone/`, linking `MakeASoundPlugin` and `eacp-core` PUBLIC) is a `STATIC` target built wherever the plugin core is; it includes eacp-core headers only, and only a standalone links it.
- `MakeASoundPluginUI` (`Plugin/UI/`, linking `MakeASoundPlugin` and `eacp-ui` PUBLIC) and `MakeASoundStandalone` (`Plugin/Standalone/`, linking `MakeASoundStandaloneCore`, `MakeASoundPluginUI` and `eacp-graphics` PUBLIC) are two more `STATIC` targets, each in its own directory's `CMakeLists.txt` and each gated on the eacp target it links existing. A plugin whose editor wants eacp-ui links `MakeASoundPluginUI` itself; only a `<Name>-Standalone` executable links `MakeASoundStandalone`. These do include eacp's UI and graphics headers, which is why they are separate targets: nothing that links only `MakeASoundPlugin` ever sees them.
- `MakeASoundPluginWeb` (`Plugin/Web/`, linking `MakeASoundPluginUI` and `eacp-webview` PUBLIC) is a `STATIC` target built where both exist (macOS, iOS, Windows), linked by a plugin core through `makeasound_add_web_editor`; it records `ParameterApi.h`'s path as `MAKEASOUND_WEB_API_HEADER` for that function.
- `MakeASoundPluginval` (`Plugin/Validation/`, linking `MakeASound` and `eacp-network` PUBLIC) is a `STATIC` target built where `eacp-network` exists on a desktop, linked only by `PluginValidator` and the test target; on Linux `eacp-network` needs libcurl's development package.
- `MakeASoundVST3` (`Plugin/VST3/`, linking `MakeASoundPlugin` and `vst3sdk` PUBLIC) is a `STATIC` target built where `vst3sdk` exists on a desktop (not iOS or Android), with the view TU and `MakeASoundPluginUI`/`eacp-graphics` PRIVATE when those exist and `NoPlugView.cpp` otherwise; it defines `MAKEASOUND_VST3_HAS_VIEW=1` PUBLIC with the view. Its entry, plist, `PkgInfo` and Linux export-map paths are the target properties `MAKEASOUND_VST3_ENTRY`, `MAKEASOUND_VST3_PLIST`, `MAKEASOUND_VST3_PKGINFO` and `MAKEASOUND_VST3_LINUX_EXPORTS`, which `makeasound_add_plugin` reads. Only a `<Name>-VST3` module links it, and no SDK type reaches a `MakeASoundPlugin` header.
- `MakeASoundAUDescribe` and `MakeASoundAU` (`Plugin/AU/`) are `STATIC` targets, the first built on every Apple platform and the second where `ausdk` exists, which is macOS alone. `MakeASoundAUDescribe` (`ComponentType.cpp`, `HostParameters.cpp`, `Plist.cpp`, `ViewPlacement.cpp`, linking `MakeASoundPlugin`, AudioToolbox and CoreFoundation PUBLIC) is SDK-free and C++20; its property `MAKEASOUND_AU_DESCRIBE_MAIN` is `DescribeMain.cpp`, the `main` of an iOS tree's `<Name>-Describe` (`<bundle name> <bundle id> <executable> <principal class> <0|1> <output>`, `writeAppExtensionPlist` over `describeModule()`). `MakeASoundAUPlistGen`, built beside them, is an executable linking nothing of ours, which loads a module and calls its `MakeASoundAUWritePlist`. `MakeASoundAU` links `MakeASoundPlugin`, `MakeASoundAUDescribe` and `ausdk` PUBLIC and is C++23 through `ausdk`. Its entry, view source, view libraries, export list and `PkgInfo` paths are the target properties `MAKEASOUND_AU_ENTRY`, `MAKEASOUND_AU_VIEW_SOURCE`, `MAKEASOUND_AU_VIEW_LIBRARIES`, `MAKEASOUND_AU_EXPORTS` and `MAKEASOUND_AU_PKGINFO` (always `../VST3/PkgInfo`), which `makeasound_add_plugin` reads. It defines `MAKEASOUND_AU_HAS_VIEW=1` PUBLIC with the view. Only a `<Name>-AU` module compiles the entry and view files, and no SDK type reaches a `MakeASoundPlugin` header.
- `MakeASoundAUv3` (`Plugin/AUv3/`, linking `MakeASoundPlugin`, `MakeASoundAUDescribe`, AudioToolbox, AVFoundation, CoreAudioKit and Foundation PUBLIC) is a `STATIC` Objective-C++ target built on `APPLE`, C++20, `-fobjc-arc -fapplication-extension`. It defines no Objective-C class: the sources on its `MAKEASOUND_AUV3_SOURCES` property are compiled by each module (and the tests) with `MAKEASOUND_AUV3_CLASS_SUFFIX` defined. `MakeASoundAUv3View` (`EmbeddedEditor.mm`, linking `MakeASoundAUv3`, `MakeASoundPluginUI` and `eacp-graphics` PUBLIC) is a second `STATIC` target where the UI tier exists, linked through `MAKEASOUND_AUV3_VIEW_LIBRARIES`.
- always use auto for variables
- platform-specific code goes in per-platform TUs (`Name-macOS.cpp`, `Name-iOS.mm`, `Name-Windows.cpp`, `Name-Linux.cpp`, `Name-Default.cpp`) selected in CMake, the way eacp and `AudioSession-*`/`DeviceQueries*` do, never under `#if` in a shared TU or header
- use modern RAII code whenever possible
- never `git commit` or `git push` without the user's explicit confirmation in that conversation: finish and verify the work, say what is ready to commit, and wait
- branches: `main` takes pull requests from `develop` alone, and `develop` takes pull requests from feature branches; neither is pushed to directly. Cut a feature branch from `develop` and open its pull request against `develop`. GitHub rulesets on both branches enforce it, and `.github/workflows/branch-policy.yml` is the check, required on `main`, that refuses a pull request into `main` from anywhere else.
